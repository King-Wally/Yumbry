# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Recipe Vault: a self-hosted, multi-user recipe manager. Every recipe/tag/category/AI-settings row belongs to exactly one user; users authenticate with email+password (open self-registration, no invite system — still meant for a trusted network, not the open internet). Two independent npm packages, `backend/` and `frontend/`, both TypeScript, built together into one Docker image and deployed with `docker compose up` (`app` + `db` services).

## Commands

Run from `backend/` or `frontend/` respectively (not the repo root — there is no root `package.json`).

```sh
npm install          # each package manages its own node_modules
npm run dev          # backend: tsx watch src/index.ts (port 3000, runs TS directly, no build step)
                      # frontend: vite dev server (port 5173, proxies /api and /uploads to :3000)
npm run typecheck    # tsc --noEmit, both packages
npm run lint         # eslint . (flat config, typescript-eslint), both packages
npm run format       # prettier --write .   /   format:check for CI-style verification
npm test             # vitest run, in both packages
npx vitest run tests/ingredient-parser.test.ts   # run a single backend test file
npx vitest run -t "parses fractional quantities" # run tests matching a name
npm run build        # backend: tsc -> dist/. frontend: tsc --noEmit && vite build (type errors fail the build)
```

Backend integration tests (`backend/tests/recipes.api.test.ts`) hit a **real** Postgres and drop/recreate the `public` schema on every run — point them at a scratch database via `TEST_DATABASE_URL`, never a real one:

```sh
TEST_DATABASE_URL=postgres://chef:changeme@localhost:5432/recipe_vault_test npm test
```

Without `TEST_DATABASE_URL` (or `DATABASE_URL`) set, that suite is skipped automatically (`describe.skipIf`) and the rest of the tests still run — this is expected in most sandboxes.

To verify a new migration's actual data-transforming logic (e.g. a one-off `UPDATE`/merge migration), running the suite above isn't enough — it only proves the migration applies cleanly to an empty schema, not that it does the right thing to pre-existing data. Don't seed that into the `db` service's real `db_data` volume. Instead spin up a fully disposable Postgres container on a different port, migrate up to (but not including) the new migration, seed the specific pre-migration state you want to exercise, run the new migration, inspect the result, then throw the container away:

```sh
docker run --rm -d --name mig-test -p 5433:5432 -e POSTGRES_USER=chef -e POSTGRES_PASSWORD=changeme -e POSTGRES_DB=recipe_vault_test postgres:16-alpine
# seed via: docker exec mig-test psql -U chef -d recipe_vault_test -c "..."
# migrate via: DATABASE_URL=postgres://chef:changeme@localhost:5433/recipe_vault_test npx prisma migrate deploy   (run from backend/)
docker stop mig-test   # cleans up automatically, --rm
```

Full stack via Docker:

```sh
cp .env.example .env
docker compose up --build
```

## Architecture

**Single deployable image, two runtime services, three build stages.** The root `Dockerfile` has `frontend-build` (`tsc --noEmit && vite build` → `frontend/dist`), `backend-build` (`npx prisma generate` to materialize `src/generated/prisma`, then `tsc -p tsconfig.json` → `backend/dist`, needs devDependencies for the `typescript` compiler), and a slim `runtime` stage that installs only production deps, copies `backend/prisma/` (schema + migrations) and `prisma.config.ts` in for `docker-entrypoint.sh`'s migration step, and copies both build outputs in (`dist/` as the server — already containing the compiled generated Prisma client from `backend-build`, so `runtime` doesn't run `prisma generate` itself — and `frontend/dist` as `public/`). The Express server serves `/api/*`, static files from `public/`, uploaded images from `/uploads` (backed by the `UPLOADS_DIR` env var, which defaults to `./uploads` relative to the process's cwd), and falls back to `index.html` for any other route (client-side routing). There is no separate frontend container — `docker-compose.yml` only defines `app` and `db`. **Uploaded photos persist via a bind mount, not a named volume** — `docker-compose.yml` mounts `./backend/uploads:/app/uploads` (not a Docker-managed named volume like `db_data`), specifically so the same files are visible whether the backend runs inside the `app` container or directly on the host via `npm run dev` (where `UPLOADS_DIR`'s default `./uploads` resolves to that same `backend/uploads/` folder). A named volume would work for the Docker-only case but isn't a host filesystem path `UPLOADS_DIR` could ever point `fs` calls at from a locally-run process. `backend/uploads/` is gitignored (already covered by the general `uploads/` entry) and `.dockerignore`'d.

**The runtime image runs as a non-root user and reports its own health.** After copying the build output in, the `runtime` stage does `RUN mkdir -p /app/uploads && chown -R node:node /app` and then `USER node` — the app process (and `docker-entrypoint.sh`'s migration step) runs as the base image's built-in unprivileged `node` user, not root. If you add a new directory/file the app writes to at runtime, make sure it's created and `chown`'d *before* the `USER node` switch, or the write will fail with `EACCES`. A `HEALTHCHECK` hits `GET /api/health` via Node's built-in `fetch` — this route is deliberately mounted before `requireAuth` (see `app.ts`) since a container-internal healthcheck has no auth cookie to send; it used to hit `GET /api/recipes` before that route required auth. Keep the healthcheck target in sync if it ever needs to move again or starts requiring something a healthcheck can't provide.

**Frontend is an installable PWA via `vite-plugin-pwa`** (`frontend/vite.config.ts`). The manifest, service worker (`sw.js`), and Workbox runtime (`workbox-*.js`) are generated at build time and land at the root of `frontend/dist`, so they're served as plain static files by `express.static(PUBLIC_DIR)` — no backend or Dockerfile changes were needed to support this. Caching is deliberately split: the app shell (JS/CSS/HTML) is precached (safe — filenames are content-hashed and Workbox diffs the precache manifest per deploy), `/api/*` is `NetworkOnly` (never cached — this is a personal Postgres-backed dataset, so staleness after an edit is worse than an occasional failed request), and `/uploads/*` is `StaleWhileRevalidate` with a 30-day/300-entry cap (recipe photos rarely change post-upload, so serving cached instantly while revalidating is a safe latency win, and the cap lets deleted/replaced images fall out eventually). `registerType: 'autoUpdate'` is used instead of prompting — single-user app, no need for an "update available" UI. `devOptions.enabled: true` is set so the manifest/SW pipeline also runs under `npm run dev`, not just the production build — otherwise Chrome DevTools reports "no manifest detected" while iterating locally, since the plugin skips injection in dev mode by default. The service worker is registered manually in `frontend/src/main.tsx` via `virtual:pwa-register` (`injectRegister: false` in the Vite config) rather than the plugin's auto-inject, and `frontend/src/vite-env.d.ts` carries the `vite-plugin-pwa/client` triple-slash reference that import needs to typecheck (it's a build-time-only virtual module, not a real file). App icons at `frontend/public/icons/` and `frontend/public/{favicon,apple-touch-icon}.png` are a placeholder "RV" monogram generated once via `frontend/scripts/generate-icons.mjs` (a one-off script, not part of the build or typecheck, using an ephemeral `sharp` install — `npm install --no-save sharp && node scripts/generate-icons.mjs` — so `sharp` never becomes a persisted dependency); swap the PNGs directly if real branding shows up later. Full install + offline behavior (service workers, therefore installability) requires a secure context — this only works as intended served over HTTPS (e.g. via the user's reverse proxy), not plain HTTP on the LAN.

**Backend layering** (`backend/src/`): `routes/` → `controllers/` → `services/` → `db/prisma.ts`, consistently for all three resources (`recipes`, `tags`, `categories`) — none of them inline query logic directly in the route file. `app.ts` builds the Express app (routes, static serving, error handler) with no `listen()` call; `index.ts` is the only file that calls `app.listen()`. Tests import `app.ts` directly via `supertest` so the app can be exercised without binding a port — **keep new server-level wiring in `app.ts`, not `index.ts`, or it won't be reachable from tests.**

**Route handlers are wrapped in `utils/async-handler.ts`'s `asyncHandler()`**, not manual `try/catch { next(err) }` boilerplate — every route registration looks like `router.get('/', asyncHandler(getRecipes))`. A controller function only needs its own `try/catch` when it intercepts a *specific* error type to produce a custom response (e.g. `postRecipe`/`putRecipe` catching `ZodError` → 400, `importRecipe` catching a bad-JSON-LD error → 400); anything else should just `throw` and let `asyncHandler` forward it to the error handler in `app.ts`. Don't reintroduce a blanket `catch (err) { next(err) }` in a controller that has no special-casing to do — it's dead boilerplate now.

**`services/recipe.service.ts` is recipe-CRUD only** (`listRecipes`, `getRecipeById`, `createRecipe`, `updateRecipe`, `deleteRecipe`, `setRecipePhoto`) — it used to also hold row/input type definitions and all tag/category logic, but that grew into three separate concerns in one file, so it's now split out:
- `services/recipe.types.ts` — every row/input type (`RecipeRow`, `IngredientRow`, `InstructionRow`, `RecipeWithRelations`, `IngredientInput`, `InstructionInput`, `RecipeInput`, `TagRef`, `CategoryRef`). These are still hand-written snake_case shapes (matching the API's JSON contract) rather than Prisma's generated camelCase model types — `recipe.service.ts`'s `toRecipeRow`/`toIngredientRow`/`toInstructionRow` (and the equivalent mappers in `auth.service.ts`/`ai-settings.service.ts`) are the one conversion point between Prisma's model shape and these API-facing types, same spirit as the `toNumber()`/ingredient-parser centralization elsewhere in this file.
- `services/tag-category.service.ts` — `upsertTags`, `upsertCategory`, `deleteOrphaned` (the generalized orphan-cleanup, parameterized by `'tags' | 'categories'`), `listTags`, `listCategories`. The `tags`/`categories` controllers import from here, not from `recipe.service.ts`.
- `db/transaction.ts` — the `Queryable` type and `withTransaction<T>()` helper (see below).

New recipe-domain logic should land in whichever of these three files actually owns the concern, rather than growing `recipe.service.ts` back into a multi-concern file.

**Any new multi-statement mutation should use `db/transaction.ts`'s `withTransaction<T>(fn)`**, not a bare `prisma.$transaction(...)` call inline in a service — `createRecipe`/`updateRecipe`/`deleteRecipe`/`registerUser` all do `return withTransaction(async (tx) => { ... })` and return whatever the callback returns (including `false`/`null` sentinels for a "not found, nothing to roll back" case — see `updateRecipe`, which just returns `false` from the callback rather than throwing, since resolving normally lets Prisma commit a transaction that changed nothing, which is harmless). `withTransaction` is a thin wrapper around `prisma.$transaction()` (see below) kept mainly so call sites read the same way they did before the Prisma migration and so there's one place to change if the transaction strategy ever needs to (e.g. isolation level, retry-on-serialization-failure).

**Backend TS uses `NodeNext` module resolution**, so relative imports keep explicit `.js` extensions even in `.ts` source files (e.g. `import { prisma } from '../db/prisma.js'` inside `recipe.service.ts`) — this isn't a leftover from the JS version, it's required: Node's ESM loader resolves against the *emitted* file, which is genuinely `.js` after `tsc` compiles `src/` → `dist/`. This also governs how the Prisma client generator emits its own output (see below) — it detects `NodeNext` from `tsconfig.json` and emits `.js`-suffixed relative imports in the generated client to match. **Frontend TS uses `Bundler` resolution** (Vite/esbuild), so it's the opposite convention: relative imports have no extension at all (e.g. `from '../api/client'`, not `.ts` or `.js`). Don't mix these conventions up between packages.

**Zod validates at trust boundaries, not everywhere.** `backend/src/schemas/recipe.schema.ts` defines `RecipeBodySchema`, parsed in `postRecipe`/`putRecipe` — a `ZodError` there means a malformed API request body, returned as a 400. Separately, `jsonld-import.service.ts` uses a much looser zod check (`JsonLdDocumentSchema`, just "is this an object or array") only to confirm `JSON.parse()` produced something indexable before searching for a Recipe node — it deliberately does **not** model schema.org's `Recipe` shape field-by-field in zod. The hand-written extraction functions there (`extractImageUrl`, `extractServings`, `extractAuthor`, `extractTagNames`, `extractInstructionTexts`) stay as procedural `unknown`-narrowing guards, because real-world recipe JSON-LD is too heterogeneous (string vs. array vs. object for the same field, missing fields, extra fields) for a strict schema without breaking real imports. If you're tempted to replace those functions with a stricter zod schema, don't — that's a deliberate design choice, not unfinished work.

**`RecipeInput` (the service layer's input type) is derived from `RecipeBody` (the Zod-inferred API shape), not hand-maintained separately.** `services/recipe.types.ts` declares `RecipeInput extends Omit<RecipeBody, 'ingredients' | 'instructions'> { ingredients?: IngredientInput[]; instructions?: InstructionInput[] }` — every scalar field (`title`, `description`, `servings`, `category`, etc.) flows from `RecipeBodySchema` automatically, so adding a field to the Zod schema doesn't require also editing a parallel hand-written interface. Only `ingredients`/`instructions` are overridden, because they represent a later pipeline stage: `RecipeBody.ingredients` is the raw client shape (a string or `{raw_text}`), while `RecipeInput.ingredients` is the already-parsed `IngredientInput[]` produced by `normalizeIngredients()` (manual entry) or `parseRecipeFromJsonLd()` (import) — see the ingredient-parsing note below. `InstructionInput` itself is `z.infer<typeof InstructionInputSchema>` re-exported from `recipe.schema.ts`, not a second hand-written interface. If you need a new field on recipes, add it to `RecipeBodySchema` first and let the service type pick it up — don't add it to `RecipeInput` directly, that reintroduces the drift this setup exists to prevent.

**Ingredient parsing is centralized, not import-only.** `services/ingredient-parser.ts` wraps the `parse-ingredient` npm package and is the single source of truth for turning a raw ingredient line into `{ amount, unit, name, is_scalable }`. It's called from two places: `jsonld-import.service.ts` (recipes imported from JSON-LD) and `controllers/recipes.controller.ts`'s `normalizeIngredients()` (manual create/edit via the form, where the frontend only ever sends raw text lines). This is why `IngredientListEditor.tsx` on the frontend just edits plain strings — the backend re-derives amount/unit/name from `raw_text` on every save, so scaling behaves identically regardless of entry path. Never bypass this by having the frontend send pre-parsed `amount`/`unit` fields for manual entries — they'll be ignored.

**JSON-LD import** has to handle real-world schema.org variance: `findRecipeNode()` unwraps `@graph`; `extractInstructionTexts()` recursively flattens `HowToSection.itemListElement` down to a flat ordered list of `HowToStep` texts; `image`/`author`/`recipeYield`/`keywords` all accept either a bare value or an array/object per the schema.org spec. `recipeCategory` and `keywords` both feed into the same `tags` table — there's no separate category column, so tag filtering and category browsing are the same mechanism. Where a field is an array per the schema.org spec (`recipeIngredient`, `keywords`), the extraction code filters to `typeof entry === 'string'` rather than casting the whole array — real-world JSON-LD sometimes has a non-string entry (e.g. a stray object) in an otherwise-string array, and the filter drops just that entry instead of the cast letting a `TypeError` escape uncaught later in `parseIngredientLine`/`.trim()`. Keep that filter-not-cast pattern for any new array field you add here.

**Postgres `NUMERIC` columns are strings by the time they leave the backend**, not numbers — `recipes.servings` and `ingredients.amount` are typed `string | null` in `RecipeRow`/`IngredientRow` (backend) and `Recipe`/`Ingredient` (frontend `src/types.ts`) for exactly this reason. This used to be `pg`'s native behavior for `NUMERIC` columns for free; Prisma instead maps `schema.prisma`'s `Decimal` fields (`servings`, `amount`) to a `Decimal.js`-like object, so `recipe.service.ts`'s `toRecipeRow`/`toIngredientRow` mappers explicitly call `.toString()` on them (`null` passes through unchanged) right at the Prisma→`RecipeRow`/`IngredientRow` conversion point — the net effect on every caller (frontend, `numeric.ts`) is unchanged. Don't "fix" these types to `number` — it'll be wrong the moment a real DB is involved, Prisma or not. On the frontend, `utils/numeric.ts`'s `toNumber(value, fallback?)` is the one conversion point for this boundary — `useScaledIngredients.ts`, `RecipeDetailPage.tsx`, and `RecipeFormPage.tsx` all use it rather than an ad hoc inline `Number(...)`; use it for any new code that needs to do math on a `servings`/`amount` value instead of adding another bare `Number(...)` call site.

**Scaling is a frontend concern.** The DB stores each recipe's base `servings` and each ingredient's parsed `amount` (nullable). `frontend/src/hooks/useScaledIngredients.ts` computes `amount * (desiredServings / baseServings)` per ingredient and `utils/format-fraction.ts` renders the result back to a rounded-to-nearest-eighth decimal with a comma separator (e.g. `1.5 → "1,5"`). Ingredients with `is_scalable: false` (parse failures, "to taste" lines, group headers) always render their original `raw_text` untouched, regardless of the servings multiplier — this is intentional per the import spec, not a bug.

**Frontend state synced from async data is adjusted during render, not via `useEffect` + `setState`.** `RecipeDetailPage.tsx` (the servings stepper) and `RecipeFormPage.tsx` (the whole edit form) both need to initialize local editable state from a React Query result once it loads, then let the user diverge from it. Both use the pattern `if (data && trackedId !== data.id) { setTrackedId(data.id); setState(...) }` directly in the component body — this is React's documented pattern for this exact case (see react.dev "you might not need an effect: adjusting state when a prop changes") and is what `eslint-plugin-react-hooks`'s `set-state-in-effect` rule is pushing toward. Don't revert this to a `useEffect` to "simplify" it; the effect version re-triggers the anti-pattern lint error and causes an extra render pass.

**Shared frontend primitives exist for chips, reorderable lists, and tag/category data — reuse them instead of recreating them.** `components/Chip.tsx` is a single active/inactive pill button; `components/FilterChips.tsx` builds the "All + one chip per item" filter row on top of it (used for browsing recipes by tag/category on `RecipeListPage.tsx`). `CategoryPicker.tsx` (the form's category selector, which also allows typing a new value) composes `Chip` directly rather than duplicating its class-ternary styling. There used to be separate `CategoryChips.tsx`/`TagChips.tsx` components with near-identical styling logic — they're gone; don't recreate a one-off chip component, use `Chip`/`FilterChips`. Likewise, `components/ReorderableListEditor.tsx` is a generic add/remove/move-by-index list editor; `IngredientListEditor.tsx` and `InstructionListEditor.tsx` are thin wrappers around it that only supply the per-row `renderItem` (a plain text input vs. a numbered textarea) — don't hand-roll another `updateLine`/`addLine`/`removeLine`/`moveLine` set for a new reorderable list. `api/queryKeys.ts` (`queryKeys.recipes(filters?)`, `queryKeys.recipe(id)`, `queryKeys.tags`, `queryKeys.categories`) plus `hooks/useCategories.ts`/`useTags.ts` are the single source of truth for those React Query keys and fetches — don't reintroduce a raw `['tags']`/`['categories']`/`['recipe', id]` array literal or a duplicate `useQuery({ queryKey: ['categories'], queryFn: getCategories })` call; import the key/hook so cache invalidation after a mutation stays consistent across pages.

**DB schema and migrations are managed by Prisma.** `backend/prisma/schema.prisma` is the single source of truth for the data model (models map to `snake_case` tables/columns via `@map`/`@@map`, since the rest of the codebase — controllers, tests, the API's JSON contract — expects e.g. `raw_text`, `is_scalable`, `user_id`); `backend/prisma/migrations/` holds the generated timestamped SQL migrations, tracked in Prisma's own `_prisma_migrations` table — there's no hand-written SQL migration file and no single `schema.sql`. `backend/prisma.config.ts` (loaded automatically by every `prisma` CLI invocation) points the CLI at the schema/migrations paths and supplies `datasource.url` from `DATABASE_URL` — this is a Prisma-major-version requirement, not a style choice: `schema.prisma` itself deliberately has no `url` field (Prisma 7 rejects one there). The `db` service in `docker-compose.yml` still doesn't bind-mount anything into `docker-entrypoint-initdb.d`; instead `backend/docker-entrypoint.sh` runs `prisma migrate deploy` before `node dist/index.js` starts, on every container start, so pending migrations apply automatically on deploy. The test suite (`recipes.api.test.ts` and friends) does the same via `tests/helpers/db.ts`'s `resetTestDatabase()` in `beforeAll`, against a freshly dropped/recreated `public` schema. To add a schema change: edit `schema.prisma`, then run `npm run db:migrate:dev` (wraps `prisma migrate dev`) against a local Postgres to generate and apply the new migration folder, and commit it. Unlike the previous `node-pg-migrate` setup, Prisma migrations have no down-migration concept and no equivalent of the old idempotent-initial-migration convention — this project predates its first deploy, so there's no pre-existing production schema to reconcile.

**The generated Prisma Client is checked out of source control but lives inside `backend/src/`, not `node_modules/`.** `schema.prisma`'s `generator client` block sets `output = "../src/generated/prisma"` and `provider = "prisma-client"` (Prisma 7's TypeScript-source generator, not the older `prisma-client-js`) — running `npx prisma generate` (or `migrate dev`, which runs it automatically) writes real `.ts` files there, which `tsc` compiles as part of the normal `src/` → `dist/` build, same as any other source file; nothing special is needed in `tsconfig.json`. `backend/src/generated/` is gitignored (and excluded from ESLint/Prettier/the Docker build context) since it's fully regenerable from `schema.prisma` — the Dockerfile's `backend-build` stage runs `npx prisma generate` before `npm run build` for exactly this reason, and the `runtime` stage does **not** regenerate it (the compiled `dist/generated/prisma` came along with the rest of `dist/` copied from `backend-build`); `runtime` only needs `backend/prisma/` (schema + migrations) and `prisma.config.ts` for `docker-entrypoint.sh`'s `prisma migrate deploy` CLI call.

**`db/prisma.ts` wraps `PrismaClient` with `@prisma/adapter-pg`, not a bare `new PrismaClient()`.** Prisma 7 requires an explicit driver adapter rather than reading a connection string straight out of `schema.prisma` — `db/prisma.ts` constructs a `PrismaPg` adapter from `DATABASE_URL` and passes it to the client. The singleton is stashed on `globalThis` outside production so `tsx watch`'s hot reload doesn't open a fresh connection pool (and exhaust Postgres's `max_connections`) on every file save — the same problem `pool.ts`'s old `pg.Pool` never had to worry about, since that pool was created once at module load and reused identically; this pattern is Prisma's standard recommendation for dev-mode hot-reloading.

**Manual create/update replace child rows wholesale.** `services/recipe.service.ts`'s `updateRecipe()` deletes and re-inserts all `ingredients`/`instructions`/`recipe_tags` rows inside one transaction rather than diffing — this is deliberate for a single-user-per-account app with small recipes, not an oversight. `createRecipe`/`updateRecipe` are also the only two places recipes get persisted; both `POST /api/recipes` and `POST /api/recipes/import` funnel through `createRecipe`. The re-insert itself is a single batched `createMany()` per table (`insertIngredients`/`insertInstructions` in `recipe.service.ts`, and `upsertTags` in `tag-category.service.ts` for the `recipe_tags` join rows) rather than looping one `INSERT`/`.create()` per row — don't reintroduce a per-row loop here, it was a real N+1 round-trip cost for recipes with many ingredients. `upsertTags`/`upsertCategory`'s "insert new rows if they don't already exist, per user" behavior — previously a single `INSERT ... ON CONFLICT` — is now `createMany({ skipDuplicates: true })` followed by a `findMany` to fetch the ids `createMany` doesn't return (tags) or a single `upsert()` on the `@@unique([userId, name])` constraint (categories, a one-row case with no batching to preserve).

**Every recipe/tag/category/AI-settings row is owned by a `user_id`, which is `NOT NULL` at the DB level — ownership is also enforced at the query layer, not by the constraint alone.** The `users` model and a `NOT NULL` `userId` FK on `Recipe`/`Tag`/`Category`/`AiSettings` are part of the initial Prisma schema/migration (this app predates its first deploy, so there was no need to phase this in across several migrations the way the old `node-pg-migrate` history did). Every service function (`recipe.service.ts`, `tag-category.service.ts`, `ai-settings.service.ts`) takes a `userId` parameter and every query is scoped with `where: { userId }` (or a `@@unique([userId, name])`-backed upsert) — the query-layer scoping is what actually prevents cross-user access; the `NOT NULL` constraint just guarantees a row can never end up ownerless in the first place. `middleware/require-auth.ts`'s `requireAuth` sets `req.userId` from the auth cookie's JWT and is applied to every `/api/recipes`, `/api/tags`, `/api/categories`, `/api/ai` router in `app.ts`; controllers read `req.userId` and pass it straight through to the service call. If you add a new recipe-domain table, give it (or its owning FK chain) the same `user_id`-scoped-by-query treatment, with `NOT NULL` on the column. `tag-category.service.ts`'s `deleteOrphaned()` takes a `userId` and scopes its `deleteMany({ where: { userId, id: { notIn: referencedIds } } })` to that user — a security review confirmed this was never actually exploitable unscoped (a tag/category row only ever gets referenced by its own owner's recipes, so a global "id not in the referenced set" scan can't delete another user's in-use row), but it was still an unnecessary full-table scan across every user on every recipe create/update/delete; scoping it lets Postgres use `idx_tags_user_id`/`idx_categories_user_id` instead.

**Auth is a stateless JWT carried in an httpOnly cookie — there's no server-side session store.** `utils/jwt.ts` is the single place that signs/verifies tokens: `signAuthToken(userId)` (via the `jsonwebtoken` package) produces a 30-day-expiry JWT, `verifyAuthToken(token)` returns the decoded `userId` or `null` on any failure (expired/invalid/malformed) rather than throwing. `postRegister`/`postLogin` in `controllers/auth.controller.ts` set the token via `res.cookie(AUTH_COOKIE_NAME, ...)` (httpOnly, `sameSite: 'lax'`, `secure: COOKIE_SECURE`, 30-day `maxAge`); `middleware/require-auth.ts` reads `req.cookies[AUTH_COOKIE_NAME]`, verifies it, and sets `req.userId` — every downstream controller only ever reads `req.userId`, never the cookie/token directly. `postLogout` just clears the cookie (`res.clearCookie`); there is deliberately **no revocation mechanism** — a JWT already issued remains valid until it expires even after "logout," which is the accepted trade-off of not running a DB-backed session/blocklist table. This replaces an earlier `express-session` + `connect-pg-simple` (Postgres-backed session store) implementation — the `session` table and its migration (`1785200000001`) were removed outright rather than superseded, since this app hadn't shipped yet when the switch happened. `services/auth.service.ts` hashes passwords with `bcryptjs` (not native `bcrypt`/`argon2` — the Docker `runtime` stage has no build toolchain for native addons) and always compares against a dummy hash when an email doesn't exist (`verifyPassword`'s fallback), so login timing doesn't leak which emails are registered. `middleware/rate-limit.ts` exports two `express-rate-limit` instances: `loginRateLimiter` (10 attempts/15min per IP, mounted on `/api/auth/register` and `/api/auth/login` only) and `apiRateLimiter` (300 req/min per IP, mounted on all of `/api/*` in `app.ts`) — the latter exists purely as a backstop against a buggy or abusive client hammering Postgres through *any* endpoint, not just auth. The cookie's `secure` flag is controlled by its own `COOKIE_SECURE` env var, deliberately **not** tied to `NODE_ENV === 'production'` — this app is normally deployed as plain HTTP on a LAN (see the PWA install note below), and a `secure` cookie is silently never sent back by the browser over HTTP, which would break login entirely rather than just weaken it. Uploaded photos (`/uploads/recipes/:id/...`) aren't user-scoped by directory structure (recipe ids are one global sequence), so `middleware/require-photo-owner.ts` checks `recipes.user_id` before `express.static` serves anything, and `middleware/require-recipe-owner.ts` runs before multer's disk storage on the photo-upload route so an unauthorized upload 404s before a file is even written. **`JWT_SECRET` has no insecure fallback** — `utils/jwt.ts` throws at import time if it's unset, unconditionally (not gated on `NODE_ENV === 'production'`): a fallback that only applies outside production is one forgotten `NODE_ENV` away from silently running a real deployment with a publicly-known, hardcoded secret, letting anyone forge a token for any user. The test suite supplies its own fixed value via `vitest.config.ts`'s `test.env`, since it never touches a real deployment secret. **`app.set('trust proxy', 1)`** is set alongside `COOKIE_SECURE` for the same reason that setting exists — this app anticipates running behind a TLS-terminating reverse proxy — because without it, `express-rate-limit` (and anything else reading `req.ip`) sees only the proxy's address, collapsing every user behind it into one shared rate-limit bucket. Configure both together for a reverse-proxy deployment; drifting one without the other reintroduces exactly the gap this paragraph is warning about.

There is deliberately **no CSRF middleware** — the previous multi-user implementation layered `csrf-csrf`'s Double Submit Cookie pattern on top of the session cookie as defense-in-depth, but that pattern exists specifically to protect an *ambient* cookie credential the browser attaches automatically to every request regardless of origin. With the JWT itself being the only auth cookie and `sameSite: 'lax'` already blocking cross-site delivery of that cookie on state-changing requests, there's no second JS-readable cookie left to steal or spoof, so the extra layer was removed along with `csrf-csrf`, `cookie-parser`'s previous CSRF-only role (it's still a dependency, now needed to read the JWT cookie itself), and the frontend's per-mutation `GET /api/auth/csrf-token` fetch in `api/client.ts`.

**Tags and categories are stored lowercase; capitalization is display-only.** `tags.name`/`categories.name` have a `@@unique([userId, name])` constraint in `schema.prisma` — two different users can each have their own "vegan" tag — but lowercasing itself is enforced only at the service layer, not by a DB constraint: `upsertTags`/`upsertCategory` in `services/tag-category.service.ts` lowercase+trim every name right before the `createMany`/`upsert` call, so this holds no matter the entry path (manual form, JSON-LD import). This is a deliberate simplification made when the schema moved to Prisma — Postgres `CHECK` constraints aren't expressible as a portable first-class Prisma schema attribute, and centralizing normalization in these two functions (the same pattern used for ingredient parsing elsewhere in this file) was judged sufficient given they're already the single write path for tag/category names. Don't add normalization anywhere else, and don't skip `upsertTags`/`upsertCategory` for a new write path — there's no DB-level backstop if you do. There is no separate "display name" — the frontend renders the capitalized look purely via Tailwind's `capitalize` utility class at each render site (`RecipeCard`, `RecipeDetailPage`, `RecipeFormPage`, `Chip`/`FilterChips`, `CategoryPicker`), not a JS helper. The two category *badges* (as opposed to filter chips) in `RecipeCard`/`RecipeDetailPage` already use `uppercase` for a deliberate all-caps style and intentionally don't also get `capitalize`. Any new code comparing or deduping tag/category names should compare case-insensitively (or lowercase first) rather than assuming input is already normalized — e.g. `RecipeFormPage.tsx`'s tag-chip list is user-typed and not lowercased client-side (`CategoryPicker.tsx`'s custom-category input snaps to an existing category's canonical casing on a case-insensitive match, so it doesn't have the same gap).

**AI features (recipe creation and improvement) support multiple providers — OpenAI, Anthropic, Google Gemini, Ollama, or any OpenAI-compatible custom endpoint — through one client, and are deliberately non-streaming and DB-configured.** The `ai_settings` table has a `provider` column (`'openai' | 'anthropic' | 'gemini' | 'ollama' | 'custom'`, nullable with **no default** — the app deliberately never assumes a provider on a user's behalf) alongside `base_url` (also nullable — hosted providers fall back to a built-in default, only `ollama`/`custom` require the user to supply one), `model`, and `api_key_encrypted` (see below), one row per user (`UNIQUE(user_id)`), DB-backed rather than only an env var, because each user may point at a different provider or a different LAN Ollama instance at runtime without a redeploy. `services/auth.service.ts`'s `registerUser()` creates a new user's placeholder `ai_settings` row with everything blank (`provider: null`, `baseUrl: null`, `model: null`) in the same transaction as the user row — a fresh user must explicitly pick a provider and fill in Settings before AI features activate (which is also why the two AI entry points are hidden until `model` is set, see the frontend paragraph below; `ai.controller.ts`'s `requireModel()` also treats a missing `provider` the same as a missing `model` for its 409, and `ai-settings.controller.ts`'s `getAiModelsHandler` returns 400 if asked to list models with no provider saved or overridden via `?provider=`). The frontend's Settings form mirrors this with a required Provider `<select>` defaulting to an empty "Select a provider..." option rather than a pre-picked one, so the browser's own form validation — not a JS default — is what forces a real choice before Save can submit. Every provider call passes `stream: false` (a deliberate v1 decision to avoid building SSE/chunked-response infrastructure); the frontend just shows a "this can take a minute" loading state instead of a token-by-token typing effect.

**The `api_key` a hosted provider needs is encrypted at rest, never returned to the client.** `utils/crypto.ts` provides `encrypt()`/`decrypt()` (AES-256-GCM via `node:crypto`), keyed by a required `AI_SETTINGS_ENCRYPTION_KEY` env var — `requireEncryptionKey()` throws at import time if it's unset or doesn't decode to exactly 32 bytes, unconditionally, following the exact `utils/jwt.ts`/`JWT_SECRET` pattern for the same reason (a fallback that only applies outside production is one forgotten `NODE_ENV` away from a real deployment silently using a public, hardcoded key). `services/ai-settings.service.ts`'s `updateAiSettings()` encrypts a provided `api_key` before storing it in `apiKeyEncrypted`; `undefined` leaves the stored key unchanged (so re-saving other fields doesn't require re-entering it) and `null` clears it. `getAiSettings()` (backing `GET /api/ai/settings`) never decrypts — it returns `has_api_key: boolean` instead of the key itself. Only `getAiSettingsForCall()` decrypts, and only server-side at the point of actually calling the provider (`ai.controller.ts`/`ai-settings.controller.ts`) — it's never used to build an API response.

**`services/ai-provider.service.ts` wraps the official `openai` npm package (the `OpenAI` client) as the one HTTP client for every provider, not a hand-rolled `fetch` call or a separate SDK per provider** — OpenAI is natively OpenAI-protocol, and Ollama, Gemini, and Anthropic each expose an OpenAI-compatible `/v1/chat/completions`-shaped endpoint (with some limitations for Anthropic, accepted as a tradeoff for not needing a fourth SDK), so `resolveBaseUrl(provider, baseUrl)` just picks the right default base URL per provider when the user hasn't overridden one (note: this is why a stored Ollama `base_url` needs a `/v1` suffix now — `http://localhost:11434/v1`, not the bare host the old `ollama-js` client took). `chatWithAi()`/`listAiModels()` each construct a fresh `new OpenAI({ baseURL, apiKey, maxRetries: 0 })` per call (cheap, and correct if the user changes provider/base URL via the Settings page between requests; `maxRetries: 0` keeps failures fast and `kind`-predictable rather than retried with backoff) and call its `.chat.completions.create()`/`.models.list()` methods. Every failure mode is normalized into a typed `AiProviderError` with a `kind` (`'unreachable' | 'bad_status' | 'malformed_response'`) rather than letting a raw SDK error escape a controller — `utils/ai-provider-error-response.ts`'s `sendAiProviderError()` maps each `kind` to an HTTP status (502 for all three). Unlike the old `ollama-js` client's un-exported `ResponseError` (which needed structural detection), the `openai` package's `APIConnectionError`/`APIError` classes are properly exported, so `toAiProviderError()` uses plain `instanceof` checks. Every `/api/ai/chat` call passes `response_format: { type: 'json_object' }` (the OpenAI-protocol equivalent of Ollama's old `format: 'json'` string mode) — deliberately, so the code doesn't depend on a specific provider/version supporting schema-constrained decoding; defensive parsing is still required afterward either way. Model listing (`GET /api/ai/settings/models`, backing the Settings page's dropdown) is attempted generically via `.models.list()` for any provider — it works for OpenAI/Ollama/most custom endpoints that implement `/v1/models`; if a provider's compat endpoint doesn't support it, the call throws and the frontend already falls back to a free-text model input, so no provider-specific gating was needed there.

**Every AI chat turn returns a JSON *envelope* — `{ reply: string, recipe: AiRecipeDraft }` — not just a conversational reply or just a structured recipe.** This is a deliberate design forced by a real constraint: JSON-object response mode requires the *entire* response to be valid JSON, so a single call can't mix free prose with strict structured data. Since the recipe-improve UX needs the model to *narrate* what it changed (not show a diff), every turn asks for both at once. `services/ai-recipe-draft.service.ts`'s `buildChatMessages(conversation, currentDraft)` builds the message array: a static system prompt (always instructs the model to return the envelope, to include the *full* current recipe every time — not just changed fields — and to attempt a best-guess recipe on turn one rather than refusing) plus a separate `system` message carrying `JSON.stringify(currentDraft)` (or a "no recipe draft yet" marker) — kept separate from the static prompt since the draft changes every turn while the instructions don't. `parseChatEnvelope(rawContent, currentDraft?)` — following the exact defensive-extraction pattern `jsonld-import.service.ts` established — strips a markdown fence if present, defaults `reply` to a generic string if missing/non-string, and extracts the nested `recipe` object via a private `extractRecipeDraft()` helper with the same tolerant per-field fallbacks as before (title defaults to `'Untitled recipe'`, servings falls back to `1`). `image_path` is the one field `extractRecipeDraft()` never reads off the model's JSON output — the LLM has no way to generate or reference an uploaded photo — instead it's carried over unchanged from `currentDraft.image_path` on every turn (`AiChatTurnRequestSchema`'s `image_path` is `z.string().nullable()`, not `z.null()`, for exactly this reason: the frontend's `toRecipeInput()` seeds a real photo path from an existing recipe when improving one, and that value must round-trip through every subsequent chat turn or the photo silently drops out of the draft after the first message). `AiRecipeDraft` itself is unchanged: deliberately identical to the **frontend's** `RecipeInput` (raw ingredient-line strings, `{step_number,text}` instructions, `servings: number`), not this backend's own `recipe.types.ts` `RecipeInput` — because the draft flows straight into the frontend's create/edit form for review, unchanged. Ingredients/instructions stay flat strings; the model is never asked to compute `amount`/`unit`/parsed fields itself — that's still `parseIngredientLine`'s job, invoked only later via the normal save path (`normalizeIngredients()`) once the user accepts a draft.

**Create and Improve are the same backend flow, differing only in their starting baseline — and the AI chat endpoint doesn't have its own save endpoint.** `routes/ai.routes.ts` mounts `GET`/`PUT /api/ai/settings`, `GET /api/ai/settings/models` (model-listing for the Settings page dropdown, optionally probing a `?base_url=` override before it's saved), and a single `POST /api/ai/chat` (stateless — takes `{messages, current_draft}` every call: the full message history plus whatever recipe state the frontend is currently showing, since the conversation is deliberately ephemeral frontend-only state, never persisted server-side). There's no `recipe_id` anywhere in this endpoint's contract — fetching an existing recipe to seed `current_draft` for the improve case is entirely a **frontend** concern (`getRecipe` + `utils/recipe-mapping.ts`'s `toRecipeInput()`); the backend only ever sees a `current_draft: AiRecipeDraft | null` and has no idea whether it's a brand-new recipe or a revision of an existing one. The endpoint returns the `{reply, recipe}` envelope and persists nothing — the user's eventual Save still goes through the unchanged `POST /api/recipes` / `PUT /api/recipes/:id`, so `createRecipe`/`updateRecipe` needed zero changes for this feature.

**Frontend: one shared chat+preview page for both Create and Improve, styled as a two-column split screen on wider viewports (chat on the left, live recipe preview on the right — think claude.ai's chat-next-to-artifact layout) and stacked chat-above-preview on mobile.** `pages/AiChatPage.tsx` is mounted at both `/create-with-ai` and `/recipes/:id/ai-improve`; `useParams<{id?: string}>()` alone determines whether it's improving (`id` present) or creating from scratch (no `id`) — there is no other branching between the two modes, they share one component end to end. State is just `messages: AiChatMessage[]` and `draft: RecipeInput | null`; in improve mode, a render-time-init block (same pattern as `RecipeFormPage`/`RecipeDetailPage`'s existing state-sync, keyed on a `seededForId` guard) seeds `draft` from `toRecipeInput(recipe)` the moment the recipe loads, with **no LLM call** for that initial seed. Every chat turn calls `chatAboutRecipe({messages, current_draft: draft})` and replaces `draft` wholesale with the response's `recipe` field — the preview panel is always just "whatever `draft` currently holds," which is also exactly what's sent as `current_draft` on the *next* turn, so the conversation and the live-updating recipe stay in lockstep with zero separate diffing logic. `components/RecipePreview.tsx` is a read-only renderer for a `RecipeInput`-shaped draft (title/category/tags/time-stats/ingredients/instructions, reusing `RecipeDetailPage.tsx`'s Tailwind vocabulary but not its `RecipeHero`/`ServingsStepper`/`TimeStat` components, since a draft has no `id`/photo/scaling) — there is no before/after diff anywhere anymore; explaining what changed is the model's job via its `reply` text, not the UI's. Save (enabled once `draft` is non-null) still hands off to the existing manual form rather than persisting directly — `navigate('/recipes/new', {state: {aiDraft: draft}})` for create, `navigate('/recipes/${id}/edit', {state: {aiDraft: draft}})` for improve — reusing `RecipeFormPage.tsx`'s existing `location.state.aiDraft` hydration mechanism unchanged in spirit, except that mechanism had to be extended: it used to only apply `aiDraft` when `!isEditing`, but Improve now needs to pre-fill the *edit* form too, so the `!isEditing` gate was dropped and the `existingRecipe`-hydration block gained an `&& !aiDraft` guard instead — otherwise the later-resolving `existingRecipe` query would clobber the earlier, synchronously-available `aiDraft` once it settled. `pages/SettingsPage.tsx` (`/settings`) now has a provider `<select>` (OpenAI/Anthropic/Gemini/Ollama/Custom) alongside the existing base-URL/model fields (base URL required only for Ollama/Custom, shown as an optional override for hosted providers) and a password-type API key field (never pre-filled with the real value — shows a "saved" placeholder plus an explicit "clear" checkbox instead, since `GET /api/ai/settings` never returns the real key). `components/AiErrorBanner.tsx`'s copy is provider-generic ("Check your AI settings") rather than Ollama-specific. **Both AI entry points are hidden until AI is actually configured** — `hooks/useAiSettings.ts` (a thin `useQuery(queryKeys.aiSettings, getAiSettings)` wrapper, the single source of truth other AI-consuming components should import rather than re-declaring the query) is used by `App.tsx` (gating the "Create with AI" nav link) and `RecipeDetailPage.tsx` (gating the "Improve with AI" button); both treat `Boolean(settings?.model)` as "configured," mirroring the exact same gate `ai.controller.ts`'s `requireModel()` uses server-side for its 409, so there's one definition of "configured" shared by frontend and backend. Layout is a single-column grid (`grid grid-cols-1`) that becomes two columns at the `md` breakpoint (`md:grid-cols-2`); DOM order is chat then preview, so the single-column mobile layout naturally stacks chat above the preview with no extra markup. Each column is a viewport-relative height (`h-[60vh] md:h-[70vh]`, `overflow-y-auto`) rather than a flex-based one, since this repo's `<main>` chrome (sticky header + footer, unconstrained height) has no fixed-height ancestor to flex-grow within; mobile gets a shorter `60vh` per column since the two columns stack instead of sitting side by side.

## Type-package gotchas already resolved once — don't redo this research

- `typescript-eslint@8.x` currently pins its `typescript` peer range to `>=4.8.4 <6.1.0`. TypeScript's own "latest" dist-tag can be ahead of that (it was mid-7.x when this repo was set up). Both packages pin `typescript` to the newest version still inside typescript-eslint's supported range — check that range again before bumping `typescript`, or ESLint will silently mismatch the compiler it lints against.
- `uuid`'s own bundled types only exist from v10+; earlier majors need `@types/uuid`, but the current `@types/uuid` publish is an empty stub ("uuid provides its own types now") with no actual declarations — installing it errors with `TS2688: Cannot find type definition file for 'uuid'`. The fix used here was bumping the `uuid` runtime dependency itself to `^11.x` (own types, no `@types/uuid` needed) rather than fighting the stub.
- **Prisma 7 is a breaking major relative to the Prisma 5/6-era tutorials most guides still describe** — three things that look like bugs are actually intentional in this version: (1) `schema.prisma`'s `datasource` block can't have a `url` field anymore (`P1012` if it does) — the connection string only lives in `prisma.config.ts`'s `datasource.url`, read from `process.env.DATABASE_URL` there. (2) `new PrismaClient()` with no arguments throws at the first query — Prisma 7 requires an explicit driver adapter (`db/prisma.ts` constructs `new PrismaPg({ connectionString: ... })` from `@prisma/adapter-pg` and passes it as `{ adapter }`); `@prisma/adapter-pg` pulls in `pg` as a real dependency, which is why `pg` is still in `package.json` even though nothing hand-writes a SQL query against it anymore. (3) The `prisma-client` generator (schema.prisma's `provider = "prisma-client"`, not the older `prisma-client-js`) requires an explicit `output` path and emits **TypeScript source**, not a prebuilt JS+`.d.ts` package — this only slots cleanly into this repo's plain `tsc` build because the generator auto-detects `NodeNext` from `tsconfig.json` and emits `.js`-suffixed relative imports to match (confirmed by generating once with no `tsconfig.json` present, which emits bare `.ts` imports instead — those don't compile under this project's `tsc` setup). If a Prisma upgrade ever changes this detection or generator default, re-verify by generating fresh and checking `src/generated/prisma/client.ts`'s import specifiers before assuming the build still works.
- `eslint-plugin-react-hooks`'s `configs['recommended-latest']` export is still in legacy eslint-plugin config shape (`{ plugins: ['react-hooks'], rules: {...} }`), not a flat-config object, despite ESLint 10 requiring flat config — spread only `.rules` into a flat config block and register the plugin object yourself under `plugins: { 'react-hooks': reactHooks }` (see `frontend/eslint.config.js`).
- Tailwind's `content` glob in `tailwind.config.js` must list the actual source extensions (`**/*.{ts,tsx}`) — leaving a stale `**/*.{js,jsx}` glob after the TS conversion doesn't error, it just silently purges almost every utility class from the production CSS bundle (looks fine in dev, breaks in the `vite build` output). If a Tailwind-based UI change looks unstyled only in the built/Docker version, check this glob first.
- `frontend/eslint.config.js`'s `ignores`, `frontend/.prettierignore`, and the root `.dockerignore` all explicitly exclude `dev-dist/**`/`dev-dist` — the PWA plugin's dev-mode service-worker output (generated because `devOptions.enabled: true`, see Architecture above), which only appears locally after running `npm run dev` at least once. Before these three ignore entries were added, a plain `npm run lint`/`format:check` after a dev session would report dozens of spurious errors from that generated Workbox bundle, or Docker would needlessly copy it into the build context. If that class of error ever reappears, check these three ignore files first rather than assuming it's a real finding.
- **`backend/tsconfig.json` is the type-checking config (`include: ["src", "tests"]`, no `rootDir`/`outDir`); `backend/tsconfig.build.json` (`extends` the former, adds `rootDir: "src"`/`outDir: "dist"`, `include: ["src"]`) is the emit config used only by the `build` script.** They used to be the same file with `include: ["src"]` only, which meant `npm run typecheck` silently never checked `backend/tests/*.test.ts` — Vitest doesn't catch this either, since it type-strips via esbuild rather than running `tsc`. They can't be merged back into one file: `tests/` sits outside `rootDir: "src"`, so once `tests` is added to `include`, a single config with `rootDir: "src"` fails the build with TS6059. The root `Dockerfile`'s `backend-build` stage explicitly `COPY`s both `tsconfig.json` and `tsconfig.build.json` in (rather than relying on a later broad `COPY backend/`) since `tsconfig.build.json extends` the other — if you rename either file, update that `COPY` line too.
- Adding a second (or third, or fourth) backend test file that does its own DB reset dance in `beforeAll` — as `recipes.api.test.ts`, `ai-settings.service.test.ts`, `ai.api.test.ts`, and `auth.api.test.ts` all do — breaks under Vitest's default concurrent-file execution: two files resetting the same `TEST_DATABASE_URL` at once race each other (`prisma migrate deploy` isn't safe to run concurrently against the same database from multiple processes), and even without that would truncate each other's tables mid-test via their own `beforeEach`. `backend/vitest.config.ts` sets `test.fileParallelism: false` for exactly this reason. All four files share the reset logic via `tests/helpers/db.ts`'s `resetTestDatabase()` (drop/recreate the `public` schema via a short-lived `pg.Pool`, then shell out to `npx prisma migrate deploy`) rather than each duplicating it — if you add another DB-touching test file, call that helper from its `beforeAll` too, and don't remove `fileParallelism: false` to "speed up" the suite without re-solving the underlying race.

## Quality bar before calling a change done

- **CI is enforced, not optional**: `.github/workflows/ci.yml` runs `typecheck`/`lint`/`format:check`/`test`/`build` for both packages on every push/PR to `main` — the `backend` job provisions a real Postgres via GitHub Actions' `services:`, so the integration suite in `recipes.api.test.ts` actually runs in CI instead of being silently skipped for lack of `TEST_DATABASE_URL`. A `docker` job also validates that `docker build .` still succeeds. Keep this workflow in sync with local tooling — if you add a new check locally (a new test file, a new lint rule), make sure CI still exercises it; don't let the workflow and the local "quality bar" below drift apart.
- Run `npm run typecheck && npm run lint && npm test` in every package you touched (not just the one with the obviously-changed file) — the ingredient parser, JSON-LD importer, and scaling hook each have call sites in the other package (see Architecture above), so a change on one side often needs the other side's tests re-run too. If you touched frontend code, also run `npm run build` (which itself runs `tsc --noEmit` before `vite build`) and check the emitted CSS/JS bundle sizes look sane, not just that it exits 0.
- Treat console/lint/test output as part of the spec, not noise to skim past: a passing suite or a clean build that still prints a warning (react-hooks rule violations, React Router future-flag notices, etc.) isn't done — fix it or it becomes the next person's mystery.
- When adding a dependency, check `npm audit` before and after so you know whether you introduced a new finding versus inheriting an existing one. The moderate/high findings already present in the vite/vitest/esbuild dev-tooling chain are dev-server-only (never shipped in the production Docker image) and accepted; a new finding against a runtime dependency (express, pg, multer, zod, etc.) is not — fix or avoid it.
- Match what's already there rather than introducing a second convention: ESM everywhere (`type: module`, no CommonJS `require`), TypeScript with `strict: true` in both packages, Tailwind's v3-style `tailwind.config.js` + `autoprefixer` (not v4's CSS-first config), functional React components with hooks (no classes), zod only at the boundaries described above (not sprinkled through internal function signatures).
- Dependency versions in this repo are deliberately pinned as a compatible set, not merely outdated — e.g. Tailwind v3/Vite v5/vitest v2/typescript-eslint's supported TS range were chosen together. Don't bump one in isolation without checking the others still resolve and `typecheck`/`lint`/`test`/`build` all still pass.
- Don't launch a browser to verify UI changes — no Chromium, Playwright, Puppeteer, or similar browser automation in this repo or environment.
