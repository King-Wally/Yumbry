# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Recipe Vault: a self-hosted, single-user recipe manager (no auth — trusted local network only). Two independent npm packages, `backend/` and `frontend/`, both TypeScript, built together into one Docker image and deployed with `docker compose up` (`app` + `db` services).

## Commands

Run from `backend/` or `frontend/` respectively (not the repo root — there is no root `package.json`).

```sh
npm install          # each package manages its own node_modules
npm run dev          # backend: tsx watch src/index.ts (port 3000, runs TS directly, no build step)
                      # frontend: vite dev server (port 5173, proxies /api and /uploads to :3000)
npm run typecheck    # tsc --noEmit, both packages
npm run lint         # eslint . (flat config, typescript-eslint), both packages
npm run format       # prettier --write .   /   format:check for CI-style verification
npm test             # vitest run, in both packages
npx vitest run tests/ingredient-parser.test.ts   # run a single backend test file
npx vitest run -t "parses fractional quantities" # run tests matching a name
npm run build        # backend: tsc -> dist/. frontend: tsc --noEmit && vite build (type errors fail the build)
```

Backend integration tests (`backend/tests/recipes.api.test.ts`) hit a **real** Postgres and drop/recreate the `public` schema on every run — point them at a scratch database via `TEST_DATABASE_URL`, never a real one:

```sh
TEST_DATABASE_URL=postgres://chef:changeme@localhost:5432/recipe_vault_test npm test
```

Without `TEST_DATABASE_URL` (or `DATABASE_URL`) set, that suite is skipped automatically (`describe.skipIf`) and the rest of the tests still run — this is expected in most sandboxes.

To verify a new migration's actual data-transforming logic (e.g. a one-off `UPDATE`/merge migration), running the suite above isn't enough — it only proves the migration applies cleanly to an empty schema, not that it does the right thing to pre-existing data. Don't seed that into the `db` service's real `db_data` volume. Instead spin up a fully disposable Postgres container on a different port, migrate up to (but not including) the new migration, seed the specific pre-migration state you want to exercise, run the new migration, inspect the result, then throw the container away:

```sh
docker run --rm -d --name mig-test -p 5433:5432 -e POSTGRES_USER=chef -e POSTGRES_PASSWORD=changeme -e POSTGRES_DB=recipe_vault_test postgres:16-alpine
# seed via: docker exec mig-test psql -U chef -d recipe_vault_test -c "..."
# migrate via: DATABASE_URL=postgres://chef:changeme@localhost:5433/recipe_vault_test npx node-pg-migrate up   (run from backend/)
docker stop mig-test   # cleans up automatically, --rm
```

Full stack via Docker:

```sh
cp .env.example .env
docker compose up --build
```

## Architecture

**Single deployable image, two runtime services, three build stages.** The root `Dockerfile` has `frontend-build` (`tsc --noEmit && vite build` → `frontend/dist`), `backend-build` (`tsc -p tsconfig.json` → `backend/dist`, needs devDependencies for the `typescript` compiler), and a slim `runtime` stage that installs only production deps and copies both build outputs in (`dist/` as the server, `frontend/dist` as `public/`). The Express server serves `/api/*`, static files from `public/`, uploaded images from `/uploads` (backed by the `UPLOADS_DIR` env var / `uploads_data` volume), and falls back to `index.html` for any other route (client-side routing). There is no separate frontend container — `docker-compose.yml` only defines `app` and `db`.

**The runtime image runs as a non-root user and reports its own health.** After copying the build output in, the `runtime` stage does `RUN mkdir -p /app/uploads && chown -R node:node /app` and then `USER node` — the app process (and `docker-entrypoint.sh`'s migration step) runs as the base image's built-in unprivileged `node` user, not root. If you add a new directory/file the app writes to at runtime, make sure it's created and `chown`'d *before* the `USER node` switch, or the write will fail with `EACCES`. A `HEALTHCHECK` hits `GET /api/recipes` via Node's built-in `fetch` — keep it in sync if that route ever moves or starts requiring something the healthcheck can't provide.

**Frontend is an installable PWA via `vite-plugin-pwa`** (`frontend/vite.config.ts`). The manifest, service worker (`sw.js`), and Workbox runtime (`workbox-*.js`) are generated at build time and land at the root of `frontend/dist`, so they're served as plain static files by `express.static(PUBLIC_DIR)` — no backend or Dockerfile changes were needed to support this. Caching is deliberately split: the app shell (JS/CSS/HTML) is precached (safe — filenames are content-hashed and Workbox diffs the precache manifest per deploy), `/api/*` is `NetworkOnly` (never cached — this is a personal Postgres-backed dataset, so staleness after an edit is worse than an occasional failed request), and `/uploads/*` is `StaleWhileRevalidate` with a 30-day/300-entry cap (recipe photos rarely change post-upload, so serving cached instantly while revalidating is a safe latency win, and the cap lets deleted/replaced images fall out eventually). `registerType: 'autoUpdate'` is used instead of prompting — single-user app, no need for an "update available" UI. `devOptions.enabled: true` is set so the manifest/SW pipeline also runs under `npm run dev`, not just the production build — otherwise Chrome DevTools reports "no manifest detected" while iterating locally, since the plugin skips injection in dev mode by default. The service worker is registered manually in `frontend/src/main.tsx` via `virtual:pwa-register` (`injectRegister: false` in the Vite config) rather than the plugin's auto-inject, and `frontend/src/vite-env.d.ts` carries the `vite-plugin-pwa/client` triple-slash reference that import needs to typecheck (it's a build-time-only virtual module, not a real file). App icons at `frontend/public/icons/` and `frontend/public/{favicon,apple-touch-icon}.png` are a placeholder "RV" monogram generated once via `frontend/scripts/generate-icons.mjs` (a one-off script, not part of the build or typecheck, using an ephemeral `sharp` install — `npm install --no-save sharp && node scripts/generate-icons.mjs` — so `sharp` never becomes a persisted dependency); swap the PNGs directly if real branding shows up later. Full install + offline behavior (service workers, therefore installability) requires a secure context — this only works as intended served over HTTPS (e.g. via the user's reverse proxy), not plain HTTP on the LAN.

**Backend layering** (`backend/src/`): `routes/` → `controllers/` → `services/` → `db/pool.ts`, consistently for all three resources (`recipes`, `tags`, `categories`) — none of them inline query logic directly in the route file. `app.ts` builds the Express app (routes, static serving, error handler) with no `listen()` call; `index.ts` is the only file that calls `app.listen()`. Tests import `app.ts` directly via `supertest` so the app can be exercised without binding a port — **keep new server-level wiring in `app.ts`, not `index.ts`, or it won't be reachable from tests.**

**Route handlers are wrapped in `utils/async-handler.ts`'s `asyncHandler()`**, not manual `try/catch { next(err) }` boilerplate — every route registration looks like `router.get('/', asyncHandler(getRecipes))`. A controller function only needs its own `try/catch` when it intercepts a *specific* error type to produce a custom response (e.g. `postRecipe`/`putRecipe` catching `ZodError` → 400, `importRecipe` catching a bad-JSON-LD error → 400); anything else should just `throw` and let `asyncHandler` forward it to the error handler in `app.ts`. Don't reintroduce a blanket `catch (err) { next(err) }` in a controller that has no special-casing to do — it's dead boilerplate now.

**`services/recipe.service.ts` is recipe-CRUD only** (`listRecipes`, `getRecipeById`, `createRecipe`, `updateRecipe`, `deleteRecipe`, `setRecipePhoto`) — it used to also hold row/input type definitions and all tag/category logic, but that grew into three separate concerns in one file, so it's now split out:
- `services/recipe.types.ts` — every row/input type (`RecipeRow`, `IngredientRow`, `InstructionRow`, `RecipeWithRelations`, `IngredientInput`, `InstructionInput`, `RecipeInput`, `TagRef`, `CategoryRef`).
- `services/tag-category.service.ts` — `upsertTags`, `upsertCategory`, `deleteOrphaned` (the generalized orphan-cleanup, parameterized by `'tags' | 'categories'`), `fetchTagsForRecipeIds`, `listTags`, `listCategories`. The `tags`/`categories` controllers import from here, not from `recipe.service.ts`.
- `db/transaction.ts` — the `Queryable` type and `withTransaction<T>()` helper (see below).
- `utils/sql.ts` — `insertValuesClause()`, a small helper for building batched multi-row `INSERT ... VALUES` clauses.

New recipe-domain logic should land in whichever of these four files actually owns the concern, rather than growing `recipe.service.ts` back into a multi-concern file.

**Any new multi-statement mutation should use `db/transaction.ts`'s `withTransaction<T>(fn)`**, not a hand-rolled `pool.connect()` → `BEGIN` → `COMMIT`/`ROLLBACK` → `client.release()` block — `createRecipe`/`updateRecipe`/`deleteRecipe` all do `return withTransaction(async (client) => { ... })` and return whatever the callback returns (including `false`/`null` sentinels for a "not found, nothing to roll back" case — see `updateRecipe`, which just returns `false` from the callback rather than manually issuing `ROLLBACK`, since committing a transaction that changed nothing is harmless).

**Backend TS uses `NodeNext` module resolution**, so relative imports keep explicit `.js` extensions even in `.ts` source files (e.g. `import { pool } from '../db/pool.js'` inside `recipe.service.ts`) — this isn't a leftover from the JS version, it's required: Node's ESM loader resolves against the *emitted* file, which is genuinely `.js` after `tsc` compiles `src/` → `dist/`. **Frontend TS uses `Bundler` resolution** (Vite/esbuild), so it's the opposite convention: relative imports have no extension at all (e.g. `from '../api/client'`, not `.ts` or `.js`). Don't mix these conventions up between packages.

**Zod validates at trust boundaries, not everywhere.** `backend/src/schemas/recipe.schema.ts` defines `RecipeBodySchema`, parsed in `postRecipe`/`putRecipe` — a `ZodError` there means a malformed API request body, returned as a 400. Separately, `jsonld-import.service.ts` uses a much looser zod check (`JsonLdDocumentSchema`, just "is this an object or array") only to confirm `JSON.parse()` produced something indexable before searching for a Recipe node — it deliberately does **not** model schema.org's `Recipe` shape field-by-field in zod. The hand-written extraction functions there (`extractImageUrl`, `extractServings`, `extractAuthor`, `extractTagNames`, `extractInstructionTexts`) stay as procedural `unknown`-narrowing guards, because real-world recipe JSON-LD is too heterogeneous (string vs. array vs. object for the same field, missing fields, extra fields) for a strict schema without breaking real imports. If you're tempted to replace those functions with a stricter zod schema, don't — that's a deliberate design choice, not unfinished work.

**`RecipeInput` (the service layer's input type) is derived from `RecipeBody` (the Zod-inferred API shape), not hand-maintained separately.** `services/recipe.types.ts` declares `RecipeInput extends Omit<RecipeBody, 'ingredients' | 'instructions'> { ingredients?: IngredientInput[]; instructions?: InstructionInput[] }` — every scalar field (`title`, `description`, `servings`, `category`, etc.) flows from `RecipeBodySchema` automatically, so adding a field to the Zod schema doesn't require also editing a parallel hand-written interface. Only `ingredients`/`instructions` are overridden, because they represent a later pipeline stage: `RecipeBody.ingredients` is the raw client shape (a string or `{raw_text}`), while `RecipeInput.ingredients` is the already-parsed `IngredientInput[]` produced by `normalizeIngredients()` (manual entry) or `parseRecipeFromJsonLd()` (import) — see the ingredient-parsing note below. `InstructionInput` itself is `z.infer<typeof InstructionInputSchema>` re-exported from `recipe.schema.ts`, not a second hand-written interface. If you need a new field on recipes, add it to `RecipeBodySchema` first and let the service type pick it up — don't add it to `RecipeInput` directly, that reintroduces the drift this setup exists to prevent.

**Ingredient parsing is centralized, not import-only.** `services/ingredient-parser.ts` wraps the `parse-ingredient` npm package and is the single source of truth for turning a raw ingredient line into `{ amount, unit, name, is_scalable }`. It's called from two places: `jsonld-import.service.ts` (recipes imported from JSON-LD) and `controllers/recipes.controller.ts`'s `normalizeIngredients()` (manual create/edit via the form, where the frontend only ever sends raw text lines). This is why `IngredientListEditor.tsx` on the frontend just edits plain strings — the backend re-derives amount/unit/name from `raw_text` on every save, so scaling behaves identically regardless of entry path. Never bypass this by having the frontend send pre-parsed `amount`/`unit` fields for manual entries — they'll be ignored.

**JSON-LD import** has to handle real-world schema.org variance: `findRecipeNode()` unwraps `@graph`; `extractInstructionTexts()` recursively flattens `HowToSection.itemListElement` down to a flat ordered list of `HowToStep` texts; `image`/`author`/`recipeYield`/`keywords` all accept either a bare value or an array/object per the schema.org spec. `recipeCategory` and `keywords` both feed into the same `tags` table — there's no separate category column, so tag filtering and category browsing are the same mechanism. Where a field is an array per the schema.org spec (`recipeIngredient`, `keywords`), the extraction code filters to `typeof entry === 'string'` rather than casting the whole array — real-world JSON-LD sometimes has a non-string entry (e.g. a stray object) in an otherwise-string array, and the filter drops just that entry instead of the cast letting a `TypeError` escape uncaught later in `parseIngredientLine`/`.trim()`. Keep that filter-not-cast pattern for any new array field you add here.

**Postgres `NUMERIC` columns come back as strings from `pg`**, not numbers — `recipes.servings` and `ingredients.amount` are typed `string | null` in `RecipeRow`/`IngredientRow` (backend) and `Recipe`/`Ingredient` (frontend `src/types.ts`) for exactly this reason. Don't "fix" these types to `number` — it'll be wrong the moment a real DB is involved. On the frontend, `utils/numeric.ts`'s `toNumber(value, fallback?)` is the one conversion point for this boundary — `useScaledIngredients.ts`, `RecipeDetailPage.tsx`, and `RecipeFormPage.tsx` all use it rather than an ad hoc inline `Number(...)`; use it for any new code that needs to do math on a `servings`/`amount` value instead of adding another bare `Number(...)` call site.

**Scaling is a frontend concern.** The DB stores each recipe's base `servings` and each ingredient's parsed `amount` (nullable). `frontend/src/hooks/useScaledIngredients.ts` computes `amount * (desiredServings / baseServings)` per ingredient and `utils/format-fraction.ts` renders the result back to a rounded-to-nearest-eighth decimal with a comma separator (e.g. `1.5 → "1,5"`). Ingredients with `is_scalable: false` (parse failures, "to taste" lines, group headers) always render their original `raw_text` untouched, regardless of the servings multiplier — this is intentional per the import spec, not a bug.

**Frontend state synced from async data is adjusted during render, not via `useEffect` + `setState`.** `RecipeDetailPage.tsx` (the servings stepper) and `RecipeFormPage.tsx` (the whole edit form) both need to initialize local editable state from a React Query result once it loads, then let the user diverge from it. Both use the pattern `if (data && trackedId !== data.id) { setTrackedId(data.id); setState(...) }` directly in the component body — this is React's documented pattern for this exact case (see react.dev "you might not need an effect: adjusting state when a prop changes") and is what `eslint-plugin-react-hooks`'s `set-state-in-effect` rule is pushing toward. Don't revert this to a `useEffect` to "simplify" it; the effect version re-triggers the anti-pattern lint error and causes an extra render pass.

**Shared frontend primitives exist for chips, reorderable lists, and tag/category data — reuse them instead of recreating them.** `components/Chip.tsx` is a single active/inactive pill button; `components/FilterChips.tsx` builds the "All + one chip per item" filter row on top of it (used for browsing recipes by tag/category on `RecipeListPage.tsx`). `CategoryPicker.tsx` (the form's category selector, which also allows typing a new value) composes `Chip` directly rather than duplicating its class-ternary styling. There used to be separate `CategoryChips.tsx`/`TagChips.tsx` components with near-identical styling logic — they're gone; don't recreate a one-off chip component, use `Chip`/`FilterChips`. Likewise, `components/ReorderableListEditor.tsx` is a generic add/remove/move-by-index list editor; `IngredientListEditor.tsx` and `InstructionListEditor.tsx` are thin wrappers around it that only supply the per-row `renderItem` (a plain text input vs. a numbered textarea) — don't hand-roll another `updateLine`/`addLine`/`removeLine`/`moveLine` set for a new reorderable list. `api/queryKeys.ts` (`queryKeys.recipes(filters?)`, `queryKeys.recipe(id)`, `queryKeys.tags`, `queryKeys.categories`) plus `hooks/useCategories.ts`/`useTags.ts` are the single source of truth for those React Query keys and fetches — don't reintroduce a raw `['tags']`/`['categories']`/`['recipe', id]` array literal or a duplicate `useQuery({ queryKey: ['categories'], queryFn: getCategories })` call; import the key/hook so cache invalidation after a mutation stays consistent across pages.

**DB schema is managed by `node-pg-migrate`.** Timestamped SQL migrations live in `backend/migrations/` (config in `backend/.node-pg-migrate.json`), applied by the `runner()` API and tracked in a `pgmigrations` table — there's no single `schema.sql` anymore. The `db` service in `docker-compose.yml` no longer bind-mounts anything into `docker-entrypoint-initdb.d` (that mechanism only fires once per volume anyway, so it can't own ongoing schema changes); instead, `backend/docker-entrypoint.sh` runs `node-pg-migrate up` before `node dist/index.js` starts, on every container start, so pending migrations apply automatically on deploy. The test suite (`recipes.api.test.ts`) runs the same migrations programmatically in `beforeAll` against a freshly dropped/recreated `public` schema. **The initial migration (`1784578878584_initial-schema.sql`) must stay `IF NOT EXISTS`-idempotent forever** — it's the one migration that has to reconcile both brand-new empty volumes and pre-existing production volumes that already had these tables from the old `schema.sql` era but no `pgmigrations` bookkeeping; later migrations don't need that guard. `node-pg-migrate` is a regular (not dev) dependency because it must run inside the production image at container start.

**Every migration must have an explicit `-- Down Migration` section, even when the operation is genuinely irreversible** — in that case the down section is a comment explaining why, not an omission. `1784627078502_delete-orphaned-tags.sql` is a one-way data cleanup with nothing to undo (its down section says so); `1784974116000_lowercase-tags-and-categories.sql`'s down section drops the two `CHECK` constraints it added (that part is genuinely reversible) but documents that the case-variant duplicate-row merge itself can't be undone (the original rows/ids are gone). Leaving the down section out entirely — as both of those migrations briefly did — makes `db:migrate:down` fail with "down migration not available" instead of self-documenting the limitation; use these two files as the template for any future data-transforming migration.

**Manual create/update replace child rows wholesale.** `services/recipe.service.ts`'s `updateRecipe()` deletes and re-inserts all `ingredients`/`instructions`/`recipe_tags` rows inside one transaction rather than diffing — this is deliberate for a single-user app with small recipes, not an oversight. `createRecipe`/`updateRecipe` are also the only two places recipes get persisted; both `POST /api/recipes` and `POST /api/recipes/import` funnel through `createRecipe`. The re-insert itself is a single batched multi-row `INSERT ... VALUES` per table — `insertIngredients`/`insertInstructions` in `recipe.service.ts` and `upsertTags` in `tag-category.service.ts` all build their `VALUES` clause via `utils/sql.ts`'s `insertValuesClause()` (or, for `upsertTags`, an `UNNEST` upsert) rather than looping one `INSERT` per row — don't reintroduce a per-row loop here, it was a real N+1 round-trip cost for recipes with many ingredients.

**Tags and categories are stored lowercase; capitalization is display-only.** `tags.name`/`categories.name` carry a `CHECK (name = lower(name))` constraint (added in `1784974116000_lowercase-tags-and-categories.sql`, which also merged any pre-existing case-variant duplicates like `"Vegan"`/`"vegan"` into one row). `upsertTags`/`upsertCategory` in `services/tag-category.service.ts` lowercase+trim every name right before the `INSERT ... ON CONFLICT` upsert, so this holds no matter the entry path (manual form, JSON-LD import) — don't add normalization anywhere else, that's the one centralized spot (same pattern as ingredient parsing above). There is no separate "display name" — the frontend renders the capitalized look purely via Tailwind's `capitalize` utility class at each render site (`RecipeCard`, `RecipeDetailPage`, `RecipeFormPage`, `Chip`/`FilterChips`, `CategoryPicker`), not a JS helper. The two category *badges* (as opposed to filter chips) in `RecipeCard`/`RecipeDetailPage` already use `uppercase` for a deliberate all-caps style and intentionally don't also get `capitalize`. Any new code comparing or deduping tag/category names should compare case-insensitively (or lowercase first) rather than assuming input is already normalized — e.g. `RecipeFormPage.tsx`'s tag-chip list is user-typed and not lowercased client-side (`CategoryPicker.tsx`'s custom-category input snaps to an existing category's canonical casing on a case-insensitive match, so it doesn't have the same gap).

**AI features (recipe creation and improvement) run through a self-hosted Ollama server, not a hosted LLM API — and are deliberately non-streaming and DB-configured.** The `ai_settings` table (migration `1785055925985_add-ai-settings.sql`) is a singleton row (`id` fixed at 1 via `CHECK (id = 1)`) holding `base_url`/`model` — DB-backed rather than only an env var, because the Ollama server may run on a different LAN machine the user wants to repoint at runtime without a redeploy. `services/ai-settings.service.ts`'s `getAiSettings`/`updateAiSettings` are the only read/write path (backing `GET`/`PUT /api/ai/settings`); `seedAiSettingsFromEnv()` (called once from `index.ts` before `app.listen`, not from `app.ts` — same reasoning as why `app.listen` itself only lives in `index.ts`) applies `OLLAMA_BASE_URL`/`OLLAMA_MODEL` env vars *only* while the row is still at its migration-seeded placeholder (`http://localhost:11434` / `NULL`), so it never clobbers a value already set via the Settings page — env vars are a first-boot convenience, not the ongoing source of truth. Ollama calls always pass `stream: false` (a deliberate v1 decision to avoid building SSE/chunked-response infrastructure); the frontend just shows a "this can take a minute" loading state instead of a token-by-token typing effect.

**`services/ollama.service.ts` wraps the official `ollama-js` client (the `ollama` npm package), not a hand-rolled `fetch` call** — `chatWithOllama()`/`listOllamaModels()` each construct a fresh `new Ollama({ host, fetch })` per call (cheap, and correct if the user changes the base URL via the Settings page between requests) and call its `.chat()`/`.list()` methods. Every failure mode is normalized into a typed `OllamaError` with a `kind` (`'unreachable' | 'timeout' | 'bad_status' | 'malformed_response'`) rather than letting a raw `ollama-js`/fetch error escape a controller — `utils/ollama-error-response.ts`'s `sendOllamaError()` maps each `kind` to an HTTP status (502 for the first three, 504 for timeout). Two `ollama-js` quirks this mapping has to work around: (1) **`ollama-js` has no built-in per-call timeout** for non-streaming requests — `chatWithOllama`/`listOllamaModels` enforce one by passing a custom `fetch` (the library's one documented extension point, via `new Ollama({ fetch })`) that wraps the real `fetch` in an `AbortController`/`setTimeout`; (2) **the `ResponseError` class `ollama-js` throws for non-2xx HTTP responses isn't exported from its public API** (confirmed by checking the published package's `dist/index.d.ts` — absent from its export list), so `isOllamaResponseError()` detects it structurally (`err.name === 'ResponseError'` + a numeric `.status_code`) instead of `instanceof`. Every `/api/ai/chat` call passes Ollama's `format: 'json'` string mode (not the newer JSON-schema-constrained mode, and no longer conditionally — every turn now returns a structured envelope, see next paragraph) — deliberately, so the code doesn't depend on a specific Ollama version supporting schema-constrained decoding; defensive parsing is still required afterward either way.

**Every AI chat turn returns a JSON *envelope* — `{ reply: string, recipe: AiRecipeDraft }` — not just a conversational reply or just a structured recipe.** This is a deliberate design forced by a real constraint: Ollama's `format:'json'` mode requires the *entire* response to be valid JSON, so a single call can't mix free prose with strict structured data. Since the recipe-improve UX needs the model to *narrate* what it changed (not show a diff), every turn asks for both at once. `services/ai-recipe-draft.service.ts`'s `buildChatMessages(conversation, currentDraft)` builds the message array: a static system prompt (always instructs the model to return the envelope, to include the *full* current recipe every time — not just changed fields — and to attempt a best-guess recipe on turn one rather than refusing) plus a separate `system` message carrying `JSON.stringify(currentDraft)` (or a "no recipe draft yet" marker) — kept separate from the static prompt since the draft changes every turn while the instructions don't. `parseChatEnvelope()` — following the exact defensive-extraction pattern `jsonld-import.service.ts` established — strips a markdown fence if present, defaults `reply` to a generic string if missing/non-string, and extracts the nested `recipe` object via a private `extractRecipeDraft()` helper with the same tolerant per-field fallbacks as before (title defaults to `'Untitled recipe'`, servings falls back to `1`). `AiRecipeDraft` itself is unchanged: deliberately identical to the **frontend's** `RecipeInput` (raw ingredient-line strings, `{step_number,text}` instructions, `servings: number`), not this backend's own `recipe.types.ts` `RecipeInput` — because the draft flows straight into the frontend's create/edit form for review, unchanged. Ingredients/instructions stay flat strings; the model is never asked to compute `amount`/`unit`/parsed fields itself — that's still `parseIngredientLine`'s job, invoked only later via the normal save path (`normalizeIngredients()`) once the user accepts a draft.

**Create and Improve are the same backend flow, differing only in their starting baseline — and the AI chat endpoint doesn't have its own save endpoint.** `routes/ai.routes.ts` mounts `GET`/`PUT /api/ai/settings`, `GET /api/ai/settings/models` (model-listing for the Settings page dropdown, optionally probing a `?base_url=` override before it's saved), and a single `POST /api/ai/chat` (stateless — takes `{messages, current_draft}` every call: the full message history plus whatever recipe state the frontend is currently showing, since the conversation is deliberately ephemeral frontend-only state, never persisted server-side). There's no `recipe_id` anywhere in this endpoint's contract — fetching an existing recipe to seed `current_draft` for the improve case is entirely a **frontend** concern (`getRecipe` + `utils/recipe-mapping.ts`'s `toRecipeInput()`); the backend only ever sees a `current_draft: AiRecipeDraft | null` and has no idea whether it's a brand-new recipe or a revision of an existing one. The endpoint returns the `{reply, recipe}` envelope and persists nothing — the user's eventual Save still goes through the unchanged `POST /api/recipes` / `PUT /api/recipes/:id`, so `createRecipe`/`updateRecipe` needed zero changes for this feature.

**Frontend: one shared chat+preview page for both Create and Improve, styled as a two-column split screen on wider viewports (chat on the left, live recipe preview on the right — think claude.ai's chat-next-to-artifact layout) and stacked chat-above-preview on mobile.** `pages/AiChatPage.tsx` is mounted at both `/create-with-ai` and `/recipes/:id/ai-improve`; `useParams<{id?: string}>()` alone determines whether it's improving (`id` present) or creating from scratch (no `id`) — there is no other branching between the two modes, they share one component end to end. State is just `messages: AiChatMessage[]` and `draft: RecipeInput | null`; in improve mode, a render-time-init block (same pattern as `RecipeFormPage`/`RecipeDetailPage`'s existing state-sync, keyed on a `seededForId` guard) seeds `draft` from `toRecipeInput(recipe)` the moment the recipe loads, with **no LLM call** for that initial seed. Every chat turn calls `chatAboutRecipe({messages, current_draft: draft})` and replaces `draft` wholesale with the response's `recipe` field — the preview panel is always just "whatever `draft` currently holds," which is also exactly what's sent as `current_draft` on the *next* turn, so the conversation and the live-updating recipe stay in lockstep with zero separate diffing logic. `components/RecipePreview.tsx` is a read-only renderer for a `RecipeInput`-shaped draft (title/category/tags/time-stats/ingredients/instructions, reusing `RecipeDetailPage.tsx`'s Tailwind vocabulary but not its `RecipeHero`/`ServingsStepper`/`TimeStat` components, since a draft has no `id`/photo/scaling) — there is no before/after diff anywhere anymore; explaining what changed is the model's job via its `reply` text, not the UI's. Save (enabled once `draft` is non-null) still hands off to the existing manual form rather than persisting directly — `navigate('/recipes/new', {state: {aiDraft: draft}})` for create, `navigate('/recipes/${id}/edit', {state: {aiDraft: draft}})` for improve — reusing `RecipeFormPage.tsx`'s existing `location.state.aiDraft` hydration mechanism unchanged in spirit, except that mechanism had to be extended: it used to only apply `aiDraft` when `!isEditing`, but Improve now needs to pre-fill the *edit* form too, so the `!isEditing` gate was dropped and the `existingRecipe`-hydration block gained an `&& !aiDraft` guard instead — otherwise the later-resolving `existingRecipe` query would clobber the earlier, synchronously-available `aiDraft` once it settled. `pages/SettingsPage.tsx` (`/settings`) and `components/AiErrorBanner.tsx` are unchanged. Layout is a single-column grid (`grid grid-cols-1`) that becomes two columns at the `md` breakpoint (`md:grid-cols-2`); DOM order is chat then preview, so the single-column mobile layout naturally stacks chat above the preview with no extra markup. Each column is a viewport-relative height (`h-[60vh] md:h-[70vh]`, `overflow-y-auto`) rather than a flex-based one, since this repo's `<main>` chrome (sticky header + footer, unconstrained height) has no fixed-height ancestor to flex-grow within; mobile gets a shorter `60vh` per column since the two columns stack instead of sitting side by side.

## Type-package gotchas already resolved once — don't redo this research

- `typescript-eslint@8.x` currently pins its `typescript` peer range to `>=4.8.4 <6.1.0`. TypeScript's own "latest" dist-tag can be ahead of that (it was mid-7.x when this repo was set up). Both packages pin `typescript` to the newest version still inside typescript-eslint's supported range — check that range again before bumping `typescript`, or ESLint will silently mismatch the compiler it lints against.
- `uuid`'s own bundled types only exist from v10+; earlier majors need `@types/uuid`, but the current `@types/uuid` publish is an empty stub ("uuid provides its own types now") with no actual declarations — installing it errors with `TS2688: Cannot find type definition file for 'uuid'`. The fix used here was bumping the `uuid` runtime dependency itself to `^11.x` (own types, no `@types/uuid` needed) rather than fighting the stub.
- `eslint-plugin-react-hooks`'s `configs['recommended-latest']` export is still in legacy eslint-plugin config shape (`{ plugins: ['react-hooks'], rules: {...} }`), not a flat-config object, despite ESLint 10 requiring flat config — spread only `.rules` into a flat config block and register the plugin object yourself under `plugins: { 'react-hooks': reactHooks }` (see `frontend/eslint.config.js`).
- Tailwind's `content` glob in `tailwind.config.js` must list the actual source extensions (`**/*.{ts,tsx}`) — leaving a stale `**/*.{js,jsx}` glob after the TS conversion doesn't error, it just silently purges almost every utility class from the production CSS bundle (looks fine in dev, breaks in the `vite build` output). If a Tailwind-based UI change looks unstyled only in the built/Docker version, check this glob first.
- `frontend/eslint.config.js`'s `ignores`, `frontend/.prettierignore`, and the root `.dockerignore` all explicitly exclude `dev-dist/**`/`dev-dist` — the PWA plugin's dev-mode service-worker output (generated because `devOptions.enabled: true`, see Architecture above), which only appears locally after running `npm run dev` at least once. Before these three ignore entries were added, a plain `npm run lint`/`format:check` after a dev session would report dozens of spurious errors from that generated Workbox bundle, or Docker would needlessly copy it into the build context. If that class of error ever reappears, check these three ignore files first rather than assuming it's a real finding.
- Adding a second (or third) backend test file that does its own `DROP SCHEMA public CASCADE` + `node-pg-migrate` `runner()` dance in `beforeAll` — as `ai-settings.service.test.ts` and `ai.api.test.ts` do, alongside the original `recipes.api.test.ts` — breaks under Vitest's default concurrent-file execution: two files running that dance against the same `TEST_DATABASE_URL` at once race on Postgres's migration advisory lock (`node-pg-migrate` fails immediately rather than waiting for it), and even without that would truncate each other's tables mid-test via their own `beforeEach`. `backend/vitest.config.ts` sets `test.fileParallelism: false` for exactly this reason. This was a non-issue when only one such file existed; if you add another DB-touching test file, the fix is already in place — don't remove it to "speed up" the suite without re-solving this.

## Quality bar before calling a change done

- **CI is enforced, not optional**: `.github/workflows/ci.yml` runs `typecheck`/`lint`/`format:check`/`test`/`build` for both packages on every push/PR to `main` — the `backend` job provisions a real Postgres via GitHub Actions' `services:`, so the integration suite in `recipes.api.test.ts` actually runs in CI instead of being silently skipped for lack of `TEST_DATABASE_URL`. A `docker` job also validates that `docker build .` still succeeds. Keep this workflow in sync with local tooling — if you add a new check locally (a new test file, a new lint rule), make sure CI still exercises it; don't let the workflow and the local "quality bar" below drift apart.
- Run `npm run typecheck && npm run lint && npm test` in every package you touched (not just the one with the obviously-changed file) — the ingredient parser, JSON-LD importer, and scaling hook each have call sites in the other package (see Architecture above), so a change on one side often needs the other side's tests re-run too. If you touched frontend code, also run `npm run build` (which itself runs `tsc --noEmit` before `vite build`) and check the emitted CSS/JS bundle sizes look sane, not just that it exits 0.
- Treat console/lint/test output as part of the spec, not noise to skim past: a passing suite or a clean build that still prints a warning (react-hooks rule violations, React Router future-flag notices, etc.) isn't done — fix it or it becomes the next person's mystery.
- When adding a dependency, check `npm audit` before and after so you know whether you introduced a new finding versus inheriting an existing one. The moderate/high findings already present in the vite/vitest/esbuild dev-tooling chain are dev-server-only (never shipped in the production Docker image) and accepted; a new finding against a runtime dependency (express, pg, multer, zod, etc.) is not — fix or avoid it.
- Match what's already there rather than introducing a second convention: ESM everywhere (`type: module`, no CommonJS `require`), TypeScript with `strict: true` in both packages, Tailwind's v3-style `tailwind.config.js` + `autoprefixer` (not v4's CSS-first config), functional React components with hooks (no classes), zod only at the boundaries described above (not sprinkled through internal function signatures).
- Dependency versions in this repo are deliberately pinned as a compatible set, not merely outdated — e.g. Tailwind v3/Vite v5/vitest v2/typescript-eslint's supported TS range were chosen together. Don't bump one in isolation without checking the others still resolve and `typecheck`/`lint`/`test`/`build` all still pass.
- Don't launch a browser to verify UI changes — no Chromium, Playwright, Puppeteer, or similar browser automation in this repo or environment. Verify frontend changes via `typecheck`/`lint`/`test`/`build` plus reading the rendered JSX/Tailwind classes carefully; if a visual check is genuinely needed, ask the user to look at it themselves rather than spinning up a browser.
- **This file is documentation, not a one-time snapshot — keep it in sync with the codebase as part of the change that makes it stale.** When you add something with real architectural weight (a new service, a new table, a non-obvious constraint, a gotcha you had to work around), add or update the relevant paragraph here in the same change, matching the existing style: bold lead-in sentence, exact file/function names, and the *why* behind the decision, not just the *what* — a future reader (human or Claude) can read the diff to see what changed, but only this file explains why it's shaped the way it is. Equally, if you notice an existing paragraph describing something that's since been renamed, removed, or superseded, fix or delete it rather than leaving it stale — an incorrect CLAUDE.md actively misleads the next reader in a way that having no CLAUDE.md at all never would.
